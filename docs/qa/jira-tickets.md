## Highest / High

### 1. Бессрочная блокировка пользователя снимается при первой попытке создать заявку

- **Тип:** Bug **Приоритет:** Highest **Метки:** security, moderation, WF-BUG-03
- **Описание:** если админ блокирует пользователя с числом дней ≤ 0, ставится `is_blocked = true` и `blocked_until = null` («на неопределённый срок»). Обработчики создания заявки и SOS считают `blocked_until = null` признаком истёкшей блокировки и снимают её. Из админки это делается вводом `-1` в поле дней: форма заменяет только 0 на 7.
- **Шаги:**
  1. Админ → `/admin/users/<id>` → дни: `-1` → «Заблокировать».
  2. Пользователь получает уведомление «заблокирован на неопределенный срок».
  3. Пользователь создаёт заявку.
- **Ожидаемо:** 403 «Вы заблокированы…», пользователь остаётся заблокированным.
- **Фактически:** заявка создана, `is_blocked = false`.
- **Где:** `backend/website/views.py:1244-1248` (block), `454-461` (`/send-task`), `2486-2497` (`/api/applications`), `2679-2690` (`/api/sos`); `frontend/app/admin/users/[id]/page.tsx` (поле дней).
- **Исправление:** не снимать блокировку в обработчиках создания; `blocked_until = null` при `is_blocked = true` считать бессрочной блокировкой. В форме и API отклонять отрицательные дни.
- **Проверка:** `test_qa_workflow.py::TestPriorityAndSpam::test_indefinite_block_holds`. Скриншот: `docs/qa/workflow/WF-BUG-03_created_while_blocked.png`.

### 2. Пароль и email попадают в URL при отправке формы входа или регистрации до загрузки JS

- **Тип:** Bug **Приоритет:** Highest **Метки:** security, frontend, WF-BUG-09
- **Описание:** у `<form>` входа и регистрации нет `method`. Если пользователь отправляет форму до гидратации React (медленная сеть, долгая загрузка бандла, ошибка JS), браузер делает обычный GET и данные уходят в строку запроса.
- **Шаги:** открыть `/login` на медленной сети (DevTools → Slow 3G), сразу ввести данные и нажать «Войти».
- **Ожидаемо:** данные не попадают в URL.
- **Фактически:** `GET /login?email=…&password=…`; пароль сохраняется в истории браузера и в логах сервера и прокси.
- **Где:** `frontend/app/login/page.tsx:73`, `frontend/app/sign-up/page.tsx:175`.
- **Исправление:** `method="post"` у обеих форм. Дополнительно — кнопка отправки неактивна до гидратации.
- **Проверка:** ручная, шаг M-19 в `QA_WORKFLOW_REPORT.md`.

### 3. Карта выбора места в форме новой заявки невидима (высота 0 px)

- **Тип:** Bug **Приоритет:** High **Метки:** frontend, map, O3-BUG-07
- **Описание:** `ApplicationMap` задаёт `height: 100%`, а у родителя в форме высоты нет. Карта занимает 0 px, точку на ней выбрать нельзя — только ввести координаты вручную.
- **Шаги:** `/applications/new` → под описанием нет карты.
- **Ожидаемо:** видна карта, клик ставит маркер и заполняет «Широта» / «Долгота».
- **Фактически:** карты нет, клик ничего не меняет.
- **Где:** `frontend/app/applications/new/page.tsx:168`; `frontend/components/common/ApplicationMap.tsx`.
- **Исправление:** обернуть `<LocationMap>` в блок с высотой, например `<div className="h-80">`.
- **Проверка:** ручная, шаг M-16 в `QA_O3_REPORT.md`. Скриншот: `docs/qa/o3/M-13_exe_error_and_no_map.png`.

### 4. Очищенное поле «Широта» или «Долгота» отправляется как 0

- **Тип:** Bug **Приоритет:** High **Метки:** frontend, validation, O3-BUG-08
- **Описание:** `Number('')` даёт `0`. Поле `required` со значением 0 считается заполненным, и заявка уходит с координатой 0.
- **Шаги:** `/applications/new` → стереть «Широта» → отправить.
- **Ожидаемо:** ошибка «Укажите широту».
- **Фактически:** заявка создана в точке (0, 76.85) — маркер в Индийском океане.
- **Где:** `frontend/app/applications/new/page.tsx:186, 201`.
- **Исправление:** хранить координаты в состоянии строками и проверять пустое значение перед отправкой.
- **Проверка:** `frontend/__tests__/new-application-upload.test.tsx` → «does not send latitude 0…» (`it.failing`). Скриншот: `docs/qa/o3/M-15_latitude_cleared_ocean.png`.

### 5. Фото с одинаковым именем в одной заявке перезаписывают друг друга

- **Тип:** Bug **Приоритет:** High **Метки:** backend, uploads, data-loss, O3-BUG-03
- **Описание:** имя файла на диске — `app_<id>_<YYYYmmdd_HHMMSS>_<name>`. Два файла `image.jpg` в одном запросе (типично для телефона) получают одно имя. Второй файл перезаписывает первый, а обе записи `ApplicationMedia` указывают на один файл.
- **Шаги:** создать заявку с двумя разными фото, оба названы `a.jpg`.
- **Ожидаемо:** 2 файла на диске.
- **Фактически:** 2 записи в БД, 1 файл.
- **Где:** `backend/website/views.py`, сборка `unique_filename` в `api_create_application` и `/send-task`.
- **Исправление:** `f"{uuid4().hex}{ext}"`.
- **Проверка:** `test_qa_o3.py::TestEdgeCases::test_same_filename_twice_keeps_both_files`.

## Medium

### 6. Лимиты заявки не соответствуют O3: описание, количество и размер фото

- **Тип:** Bug **Приоритет:** Medium **Метки:** O3, validation, O3-BUG-01, O3-BUG-02, O3-BUG-04
- **Описание:** требования O3 — описание до 1000 символов, до 3 фото, каждое до 10 МБ. Сейчас: 5000 символов, количество не ограничено, 50 МБ на файл. Это и на бэкенде, и в форме.
- **Ожидаемо:** 1001 символ, 4 фото и файл 10.1 МБ отклоняются с понятной ошибкой; 1000 символов, 3 фото и файл 10.0 МБ принимаются.
- **Фактически:** всё принимается.
- **Где:** `backend/website/views.py:26` (`MAX_DESCRIPTION_LENGTH`), `backend/website/validation.py:7` (`MAX_FILE_BYTES`), дублирующие проверки 50 МБ в `views.py`; `frontend/app/applications/new/page.tsx:68, 137`.
- **Исправление:** вынести `MAX_DESCRIPTION = 1000`, `MAX_PHOTOS = 3`, `MAX_FILE_BYTES = 10 * MiB` в `validation.py`, удалить дубли в `views.py`, в форме использовать те же числа.
- **Проверка:** `test_qa_o3.py` → `test_description_1001_characters_rejected`, `test_fourth_photo_rejected`, `test_file_10_1_mb_rejected`; Jest → тесты с O3-BUG-01/02/04.

### 7. Содержимое загружаемого файла не проверяется (.exe под видом .jpg)

- **Тип:** Bug **Приоритет:** Medium **Метки:** security, uploads, O3-BUG-05
- **Описание:** проверяется только расширение. Исполняемый файл, переименованный в `photo.jpg`, принимается и отдаётся как `image/jpeg`.
- **Где:** `backend/website/validation.py`, `validate_upload`.
- **Исправление:** проверять сигнатуру файла, например через Pillow `Image.verify()` для изображений.
- **Проверка:** `test_qa_o3.py::TestUploadBoundaries::test_exe_renamed_to_jpg_rejected`.

### 8. Просроченные заявки остаются на карте и принимают отклики

- **Тип:** Bug **Приоритет:** Medium **Метки:** lifecycle, WF-BUG-01
- **Описание:** `expires_at` нигде не учитывается. CLI `check-expired-applications` только отправляет напоминание и не закрывает заявку.
- **Ожидаемо:** заявка с `expires_at < now` не показывается на карте и в списке, отклик на неё → 400.
- **Фактически:** видна, отклик принимается.
- **Где:** `views.py:2292-2410` (карта и список), `views.py:1903` (respond), `__init__.py:109-147`.
- **Исправление:** фильтр `expires_at > now()`; CLI-задачу запускать по расписанию.
- **Проверка:** `test_qa_workflow.py::TestLifecycle::test_expired_request_leaves_map`.

### 9. Модератор может одобрить или отклонить уже решённую заявку

- **Тип:** Bug **Приоритет:** Medium **Метки:** moderation, lifecycle, WF-BUG-02
- **Описание:** approve, reject и mark-false не проверяют текущее состояние. Решённую заявку можно «отклонить», и автор получит «Заявка отклонена» уже после того, как ему помогли.
- **Ожидаемо:** 409 для закрытых заявок.
- **Где:** `backend/website/views.py:1629-1783`.
- **Исправление:** таблица допустимых переходов (например, `pending → approved/rejected`, `approved → rejected`), остальные → 409.
- **Проверка:** `test_qa_workflow.py::TestLifecycle::test_moderation_of_closed_request_refused`.

### 10. Волонтёры не получают уведомление, когда модератор отклоняет одобренную заявку

- **Тип:** Bug **Приоритет:** Medium **Метки:** notifications, WF-BUG-05
- **Описание:** волонтёр уже принят и, возможно, едет помогать, а заявку сняли — уведомления нет, его отклик остаётся `accepted`.
- **Где:** `backend/website/views.py:1697-1759`.
- **Исправление:** при reject одобренной заявки уведомлять всех `accepted` и переводить их отклики в `cancelled`.
- **Проверка:** `test_qa_workflow.py::TestNotifications::test_accepted_volunteer_notified_when_request_rejected`.

## Нужно решение команды (не баги)

### 17. Сколько волонтёров автор может принять на одну заявку?

- **Тип:** Task / Decision **Приоритет:** High **Метки:** product, BUG-03
- **Суть:** в `docs/scope-october-2026.md` сказано: «The author accepts several helpers if necessary». Сейчас при принятии второго волонтёра первый молча отменяется: он получает «Отклик принят», а следом «Отклик отклонен». Проверено в браузере, шаг M-11.
- **Варианты:** а) разрешить несколько принятых — тогда убрать отмену в `accept_response` (`views.py:1946-1995`) и добавить блокировку от гонки; б) оставить одного — тогда обновить требования и показывать автору предупреждение перед заменой.

### 18. Может ли волонтёр откликнуться снова после отклонения?

- **Тип:** Task / Decision **Приоритет:** Low **Метки:** product, WF-OBS-04
- **Суть:** из-за ограничения `uq_response_volunteer` отклонённый волонтёр больше никогда не может откликнуться на эту заявку, даже если автор передумал. Требования этот случай не описывают.
- **Варианты:** а) так и задумано — оставить; б) разрешить — переоткрывать существующий отклик (`cancelled → pending`) вместо создания нового.

### 21. SOS публикуется без модерации — обновить требования?

- **Тип:** Task / Decision **Приоритет:** Low **Метки:** product, WF-OBS-06
- **Суть:** в `main` SOS сразу виден на карте (лимит 3 в час), а `docs/scope-october-2026.md` описывает модерацию SOS. Нужно либо обновить документ, либо вернуть модерацию.
